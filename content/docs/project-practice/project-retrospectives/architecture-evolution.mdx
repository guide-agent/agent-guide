## 面试题：如何说明一次架构演进是必要的？

### 回答框架

用旧系统的具体瓶颈、备选方案和验证结果说明变更，而不是用组件数量证明先进。演进应可分阶段验证，并保留迁移、兼容和回滚方案。没有实测时，应将预期收益与已经观察到的结果分开。

### 关键机制与取舍

- 先量化或复现问题：上下文过长、任务丢失、故障半径或成本放大。
- 优先验证最小结构调整，再决定是否引入多 Agent、异步执行或独立服务。
- 数据和任务状态迁移考虑双版本兼容，长任务完成策略与回滚窗口。

### 场景与失败处理

从内存任务转持久化队列，价值在于重启恢复与负载隔离，但会增加至少一次执行和重复消费风险；设计必须同步补幂等与任务所有权。

### 常见追问

**什么时候不该重构？** 瓶颈没有证据、收益小于迁移风险或现有系统已满足约束时。

**演进成功怎么证明？** 对比同分布任务的可靠性、成本与维护指标，记录新引入的失败模式。
