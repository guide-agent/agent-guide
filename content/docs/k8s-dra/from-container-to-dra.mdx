## 30 秒先记住一句话

DRA 让 Kubernetes 更明确地知道“有哪些设备、任务要什么条件、最终分到了什么”。它改善的是**设备需求表达与分配协作**，不是 GPU 虚拟化本身。切分显存、限制使用或隔离故障，仍需要相应硬件与软件机制。

没接触过 GPU 的读者，可以先看 [GPU 扫盲](/docs/gpu-virtualization/gpu-basics)。本篇不要求先背 YAML，先把职责关系弄清楚。

## 容器里为什么不会自动出现 GPU？

镜像中有模型代码，不代表容器已经能访问宿主机上的设备。至少要逐层确认：

1. **宿主机能用**：硬件、驱动和操作系统正常。
2. **容器能接入**：运行时提供正确的设备访问和所需驱动侧组件。
3. **应用能运行**：镜像内的库与驱动兼容，应用确实能完成一项设备计算。
4. **集群会分配**：Kubernetes 能发现资源，并把任务放到满足条件的节点。

这几个条件是相互配合的，不是互相代替的。“节点上能看到卡”“Pod 被调度”“容器能列出卡”“模型成功推理”，分别证明不同环节。

## 先理解传统 Device Plugin 路径

以常见的 NVIDIA GPU 扩展资源为例，Pod 可以请求整数数量的 `nvidia.com/gpu`。这只是资源名称示例，实际资源如何暴露由插件配置决定。

```text
插件发现设备并向 kubelet 上报
    -> 节点暴露可调度的扩展资源数量
    -> 调度器选择满足完整 Pod 条件的节点
    -> kubelet 与插件完成具体设备分配、准备
    -> 运行时接入设备，容器启动
```

这个模型很适合表达“要几份资源”。如果暴露的是 MIG 实例或时间片共享份额，一份资源也可能不是一张独占物理卡。**调度器数的是插件声明的资源单位，不是从名字推断硬件隔离。**

扩展设备资源使用整数计数，不能把 `nvidia.com/gpu: 0.5` 当成原生的“半卡”申请方式。厂商可用其他资源名称、标签、插件和共享方案表达更细需求，但这些机制必须各自解释。

## 那为什么还需要 DRA？

想象两台节点都报告“有 2 份 GPU 资源”，但型号、设备属性或可用的实例规格不同。仅看一个数量，无法完整表达所有选择条件。

Device Plugin 方案可以通过不同资源名、节点标签和扩展机制区分设备，因此不能说它“完全不会分类”。DRA 的改进是：使用标准资源对象描述设备信息和任务声明，让设备匹配与分配结果更明确地进入 Kubernetes API。

这对需要按设备属性选型、独立跟踪声明状态或协调设备生命周期的任务更有价值。只是稳定的整卡独占场景，不必为了“更新”就立即迁移。

## 四个对象，按申请设备的过程记

下面用“领取实验设备”帮助记忆；类比不表示 DRA 提供了按小时预约等额外功能。

| 对象 | 可以怎样记 | 实际职责 |
| --- | --- | --- |
| `ResourceSlice` | 库存清单 | 驱动发布设备及属性等信息 |
| `DeviceClass` | 设备选择规则 | 定义可选的一类设备及相关规则或配置 |
| `ResourceClaim` | 填好的申请单 | 表达具体需求，并记录分配结果 |
| `ResourceClaimTemplate` | 申请单模板 | 用于自动创建工作负载所需声明 |

例如，任务需要“满足某容量条件的一张设备”，首先要确认驱动实际发布了对应属性，再通过受支持的声明结构表达需求。DeviceClass 不是一张实体卡，Template 也不是预先划好的 GPU 分区。

不要直接复制网上的属性名。不同驱动发布的属性、单位、字段和特性支持可能不同；不存在“只改 apiVersion，就适配任意集群”的保证。对象范围与具体职责见 [核心资源对象](/docs/k8s-dra/core-resources)。

## DRA 的链路，比“选中设备”多几步

```text
驱动发布设备信息
    -> 工作负载引用 Claim 或模板
    -> 结合设备条件与 Pod 条件进行分配、调度
    -> 分配结果记录在声明状态中
    -> kubelet 与节点驱动准备设备
    -> 容器运行时接入设备，应用验证可用
```

这是便于理解的主线，不是承诺所有版本都采用完全一样的内部时序。分配、预留、节点准备和解除准备的细节，应结合目标版本与驱动确认。

**选中了设备，不等于能使用设备。** Claim 已有分配结果，仍可能因为节点准备失败、设备描述不匹配或容器库不兼容而无法运行。反过来，Pod Pending 也不一定是 GPU 不够，可能是 CPU、内存、亲和性或数据卷约束不满足。

## 最容易混淆的五件事

### DRA 与 GPU Operator

DRA 是设备资源管理机制；GPU Operator 用于管理所支持的 GPU 软件组件。某个版本的 Operator 是否部署某种 DRA 驱动，属于产品集成能力，需要另外核对，不能把两者当同义词。

### DRA 与 MIG、时间片、HAMi

DRA 主要回答“怎样表达和分配设备”，MIG、时间片及具体共享后端回答“设备内部怎样切分、复用或限制”。一个系统可能把不同层组合起来，但兼容性、库存归属和资源语义都需要验证。

### DRA 与 CDI

CDI 是容器设备接口，规范运行时如何根据设备描述完成接入。它不是显存隔离器，也不会因为设备进入容器就自动限制其算力。见 [驱动与 CDI](/docs/k8s-dra/driver-cdi)。

### DRA 与队列、批调度

设备分配不等于决定“哪个团队先运行”。队列准入、团队配额、作业优先级和一组任务的协同启动是另一类问题，通常需要对应的作业管理或调度能力。

Kueue、Volcano 等项目常出现在这一层的讨论中，但它们的职责也不完全相同。不要因为系统引入了其中一个名字，就假定所有排队、抢占、DRA 集成与隔离能力都已生效。

### 共享声明与独立配额

多个工作负载引用同一个 Claim，是声明与使用关系；多个独立 Claim 消费同一设备的部分容量，又是不同机制。二者都不能自动证明每个任务有独立显存或固定计算性能，需分别核对 API 特性、驱动计量与底层限制。

## 一个完整例子：两支团队各运行一个模型

假设两支团队都希望用同一类 GPU，资源又不足以让所有任务同时独占运行。应拆成四个问题：

1. **谁先开始？** 按团队配额、优先级和队列规则决定，不由 MIG 分区代替。
2. **选择哪台节点、哪个设备？** 检查需求与库存，以及 CPU、内存、存储等共同约束。
3. **是否允许共用？** 根据硬件、驱动和共享方案确认，不能只看声明对象是否支持引用。
4. **共用后是否满足要求？** 验证显存占用、请求延迟和邻居故障影响，不能只看两个 Pod 都变成 Running。

这就是为什么 DRA 和 GPU 虚拟化值得分成两个栏目：它们紧密相关，但解决不同层的问题。

## 从哪里开始排障？

- **对象创建失败**：先核对 API、字段、权限、特性和驱动版本。
- **Claim 没有分配**：检查库存、设备条件、占用和驱动发布信息。
- **分配完成但 Pod 等待**：检查事件、其他调度约束以及节点准备阶段。
- **容器启动但应用失败**：检查设备身份、运行时、库兼容和实际计算错误。
- **任务结束后资源未回收**：核对 Claim 来源、引用关系、所有者与清理状态，别直接删除仍在使用的共享声明。

更完整的证据清单见 [DRA 排障](/docs/k8s-dra/troubleshooting)。排查时先收集状态，不要把反复删除 Pod 或重启驱动当成通用修复。

## 面试自测

**DRA 是否要取代所有 GPU 共享软件？** 不。它没有代替硬件和软件实现具体隔离、限额的职责。

**Device Plugin 和 DRA 能同时用吗？** 可以评估分节点或明确设备归属的共存方式，但不能让同一物理资源被两套机制重复当作空闲库存分配。

**要部署 DRA，先问什么？** 先明确任务需求，再核对 Kubernetes API、功能开关、驱动、硬件和运行时支持。核心 API 稳定不代表所有共享、容量或拓扑相关特性都同样成熟。
