## 文档目标

这套题库不仅记录“标准答案”，还要保留问题背后的判断依据。面试官可以据此设计追问，候选人可以用它检查知识盲区，工程师也可以把真实故障复盘沉淀为题目。

## 单题模板

答案应让没做过这个技术的人也能先听懂，再逐层深入。新增或改写题目时建议使用以下结构：

```mdx
## 问题：如何避免 Agent 无限循环？

### 30 秒回答

不能只靠模型自己判断何时停。程序要限制步骤数、总时间和费用，并检查重复动作是否带来新信息。达到上限时说明未完成原因，不能把强制结束包装成成功。

### 用一个例子理解

查物流连续几次都返回空结果，再查同样内容并没有进展。应确认订单号是否正确，必要时请用户补充，而不是无限重试。

### 关键机制与取舍

- 区分完成、失败、预算耗尽和等待人工。
- 限制单次动作，也限制整个任务，避免子任务绕开预算。
- 对重复动作比较新增证据，不能只检查文字有没有变化。

### 常见误区

只设置最大轮数，没有区分正常结束、可重试错误和不可恢复错误。

### 常见追问

**达到最大轮数就算完成吗？** 不算，任务是否成功要看业务目标和真实结果。

**保存进度后能直接重跑吗？** 先核对已执行的外部动作，避免重复发信、扣款或写入。

## 参考资料

列出实际阅读过的官方说明或固定提交文件，说明版本和验证范围。
```

## 三层阅读法

1. **先能说清楚**：只读“30 秒回答”，尝试不看稿讲出是什么、解决什么问题、有什么限制。
2. **再能举例子**：用一个输入、动作和结果解释机制；例子是帮助理解，不是技术保证。
3. **最后应对追问**：读机制、失败处理、计算和来源，说明为什么这样选、怎样验证。

“30 秒”是短答长度目标，不要求背固定措辞。已有长文可以保留分节讲解，但开头应给读者一个容易理解的入口。没有实际项目经验时，明确说“如果设计这个系统，我会……”，不要把教学例子说成个人上线经历。

## 质量标准

- 结论必须可验证；不确定时说清条件和未知项，避免把“可能更好”写成没有依据的推荐。
- 先用白话定义，再给必要术语。首次出现的缩写应解释，例如 TTFT 是等到第一个输出 token 的时间。
- 一个例子讲清一个机制，不用多层类比替代技术说明；类比不适用的地方要点明。
- 有计算就列出假设、单位和公式；假设数字不能写成性能实测。
- 工程题至少包含一个失败路径和对应恢复策略。
- 涉及版本行为时记录版本与验证日期。
- 引用外部材料时优先使用官方文档、标准或原始论文。
- 示例不得包含真实密钥、个人数据或内部地址。

## 参考与答案边界

本轮重点主题采用“主问题、30 秒回答、具体例子、机制与取舍、失败场景、带答案的追问、参考资料”组织内容；其他已有页面保留回答框架。面试合集用于发现考点，具体协议、API 和厂商能力优先核对官方资料。不是每个页面都需要重复所有小标题，应以读起来清楚为准。

- GitHub 来源引用固定提交，完整清单见 [参考资料](/docs/references)。第三方图像与整篇答案不直接搬运。
- “场景与失败处理”通常为教学案例；没有实际记录时，不描述成本站或作者真实经历。
- 项目页给出设计与验收方法，不代表附带了可部署的完整项目；也不使用参考仓库的模板业绩充当实测结果。
- 概念核对、静态源码阅读、文档构建和真实集群验证是不同层次，应分别报告。
- 对 GPU、驱动和协议版本，不将局部默认值或单个型号实验泛化为全部产品保证。

## 新增页面

### 图片放在项目内

文档插图优先放到 `public/images/docs/`，在 Markdown 中使用 `/images/docs/...` 的本地路径。保留原图及来源记录，不要把获取图片尺寸所需的远程请求变成开发和构建的前置条件。

Fumadocs 会在编译时处理 Markdown 图片。直接引用远程图片可能因网络超时导致整页编译失败；仅让浏览器能够访问该地址，或只在某次构建中启用代理，都不能消除这个依赖。新增本地图片后，还应验证生产构建和页面显示。

### 正文与导航

在 `content/docs` 下新增 `.md` 或 `.mdx` 文件即可。使用 YAML frontmatter 定义标题和摘要：

```md
---
title: 页面标题
description: 一句话说明页面内容。
---
```

目录顺序由同级 `meta.json` 的 `pages` 字段控制。完成编辑后运行：

```bash
pnpm lint
pnpm types:check
pnpm build
```
