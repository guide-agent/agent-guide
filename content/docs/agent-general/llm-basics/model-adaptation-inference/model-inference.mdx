## 面试题：如何解释 Prefill、Decode 和 KV Cache 的性能差异？

### 30 秒回答

生成回答大致分两段：Prefill 先处理输入，Decode 再逐个生成 token。KV Cache 保存历史内容计算出的键和值，让下一步不用重复生成这些历史表示。输入长会增加前期工作，输出长会延长生成过程；高并发还会争用显存和计算资源。

### 用一个例子理解

让模型阅读一份长合同后回答“是否允许转租”，首字出来之前需要处理合同；首字出来后则继续逐步生成解释。KV Cache 像计算过程的便签，不是最终答案缓存，更不是用户长期记忆。服务慢时要分清是在排队、读输入，还是生成输出。

### 关键机制与取舍

- KV Cache 随并发、序列长度、层数、KV 头数和元素字节数增长；粗估可用 2×B×S×L×Hkv×D×字节数。
- 连续批处理提升利用率，但请求长度差异、调度与内存碎片会影响尾延迟。
- 量化、前缀缓存、分页和并行分别改变不同瓶颈；固定模型、硬件和输入输出分布再比较。

### 算一遍：一个请求需要多少 KV Cache？

下面是假设模型的容量估算，不是某个模型或 GPU 的实测。对每层都保留完整历史 K/V 的常见结构：

```text
KV 字节数 ≈ 2 × B × S × L × Hkv × D × E

2：K 和 V 两份
B：同时保留缓存的序列数
S：每条序列已缓存的 token 数（含输入和已生成部分）
L：层数
Hkv：KV 头数，不一定等于查询头数
D：每个头的维度
E：每个缓存元素的字节数
```

设 B=1、S=8192、L=32、Hkv=8、D=128、E=2，得到 `1,073,741,824` 字节，也就是 **1 GiB**。若同时保留 8 条同样长的独立序列，理论 K/V 数据约为 **8 GiB**，尚未包含权重、临时缓冲、管理开销和内存碎片。

因此，“权重能放进显存”不等于“服务能支持很多长对话”。滑动窗口、缓存量化、前缀共享、多卡切分或其他注意力结构会改变实际占用，不能对所有模型套同一个结果。

### 三种“慢”要分开

- **排队慢**：请求还没轮到执行，先看在途任务和服务容量。
- **首字慢**：从请求发出到第一个 token 的时间叫 TTFT，其中可能包含排队、检索、网络和 Prefill，不全是模型计算。
- **生成慢**：首字之后每个 token 的平均生成耗时可用 TPOT 描述；输出越长，总占用时间一般越长。

**采样参数不是性能或准确性的万能开关。** Temperature 调整候选概率的尖锐程度，top-k 限制候选个数，top-p 保留按概率排序后累计达到阈值的一小组候选。低温不等于事实正确，温度为零也不能保证跨服务、版本和硬件逐字复现。

### 场景与失败处理

低并发测得延迟很好，高峰却长时间不出首字。先查看排队时间和 KV 容量，不应仅更换采样参数；限制在途请求或输入长度需明确产品降级行为。

### 常见追问

**KV Cache 会存全部对话文本吗？** 缓存存中间张量，不是可供业务任意检索的长期记忆。

**GPU 利用率高代表服务好吗？** 不代表；还要看任务完成率、TTFT、TPOT、吞吐和尾延迟。
