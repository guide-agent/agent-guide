## 30 秒先建立全貌

GPU 擅长把大量相似计算并行处理，但不保证所有程序都比 CPU 快。使用它至少要过三关：**数据装得下，数据搬得动，计算做得快**。虚拟化或共享是在这些有限资源上安排多个任务，不是凭空增加一张卡的能力。

读完本篇，再看 [共享方案比较](/docs/gpu-virtualization/sharing-comparison)；想知道 Kubernetes 怎样分配这些设备，接着看 [从容器使用 GPU 到 DRA](/docs/k8s-dra/from-container-to-dra)。

## 显存、算力、带宽，各自解决什么问题？

可以暂时把 GPU 想成一个加工车间：显存是放材料和半成品的工作区，计算单元负责加工，带宽决定材料搬运速度。这个类比只帮助区分资源，不表示硬件一定按三步串行工作。

| 概念 | 白话解释 | 典型问题 |
| --- | --- | --- |
| 显存容量 | 一次能在设备上放多少数据 | 模型权重、缓存或临时结果放不下，出现显存不足 |
| 计算吞吐 | 一段时间能做多少指定类型的运算 | 大量矩阵计算需要较长时间 |
| 显存带宽 | 数据在显存与计算单元之间搬得多快 | 计算单元等数据，增加计算能力也未必更快 |
| 设备互连 | GPU 与主机、其他 GPU 之间如何交换数据 | 多卡任务花很多时间等待传输或同步 |

**显存大，不等于计算更快。** 两张卡都能装下模型，响应速度也可能不同。比较 TFLOPS 等峰值指标时，要核对数值精度、是否采用稀疏计算等条件，不能把不同口径直接相除。

**CPU 也不会因此消失。** 读取文件、准备输入、执行部分算子、提交 GPU 工作和处理网络仍可能在主机侧完成。数据库查询慢时，换更贵的 GPU 未必能改善用户等待时间。

## 先认识几个经常出现的名字

- **SM**：NVIDIA GPU 中组织线程执行的计算单元。这里只需知道“卡内还有更细的执行资源”，暂时不必背每代硬件有多少个。
- **HBM / GDDR**：常见显存技术，容量与带宽都要结合具体产品看；不是两种 GPU 虚拟化方式。
- **Kernel**：提交给 GPU 执行的一段计算程序，这里的 kernel 不指 Linux 内核。
- **PCIe、NVLink 等互连**：承担设备间传输。支持哪些连接、实际拓扑是什么，比只数 GPU 张数更重要。

一个四卡任务不一定比单卡快四倍。如果每一步都要等其他卡交换结果，通信和同步就可能成为主要成本。

## 驱动、CUDA、Container Toolkit、GPU Operator 怎么区分？

它们不是“装一个就能替代其他所有组件”的关系。

| 组件 | 主要职责 | 不能据此推出什么 |
| --- | --- | --- |
| GPU 驱动 | 让操作系统和用户态程序访问、管理设备 | 宿主机能识别卡，不代表容器和应用一定能用 |
| CUDA 运行时与库 | 为应用提供提交计算、管理设备内存等能力 | 不代表 Kubernetes 已经能分配 GPU |
| CUDA Toolkit | 提供开发所需的编译器、库及工具等 | 运行现成程序不一定需要完整开发工具链 |
| NVIDIA Container Toolkit | 将设备访问及所需驱动侧组件接入容器 | 不是切分显存或分配业务配额的工具 |
| Device Plugin / DRA 驱动 | 将设备发现与分配相关能力接入 Kubernetes | 不自动保证硬件隔离或服务延迟 |
| GPU Operator | 自动部署、管理所支持的 GPU 软件组件 | 不是业务作业排队器，也不是单独的虚拟化机制 |

普通容器共享宿主机内核，不能把安装 GPU 镜像理解为给它配了一套完全独立的底层驱动。镜像里的用户态运行时、框架与节点驱动仍需兼容。

### 一个很常见的版本误会

`nvidia-smi` 中的 CUDA 相关版本信息反映驱动支持能力，不能直接当成“容器里安装的 CUDA Toolkit 版本”。不同工具版本的字段名可能变化。主机驱动、容器运行时、框架构建信息和开发工具版本，应分别核对。

例如，宿主机能运行 `nvidia-smi`，而应用仍报告运行时不匹配，是可能发生的。应查看具体错误与兼容要求，不要为了让两个版本字符串相同就随意升级生产驱动。

## 一份推理请求怎样真正用到 GPU？

1. 应用在 CPU 侧接收请求、准备输入。
2. 通过运行时与驱动使用已授权的 GPU，加载权重并申请所需显存。
3. 将输入或中间数据送到设备，提交计算；多卡场景还需要通信。
4. 保存后续生成需要的缓存，继续计算，最后把结果返回用户。
5. 任务结束后，应用或框架决定哪些内存可以复用或释放。

这些步骤可能重叠执行；这里只描述职责，不是某个框架的固定调用时序。Kubernetes 负责的设备分配与容器接入发生在另一层，并不会替应用完成模型加载。

## GPU 虚拟化、共享与硬切分是什么关系？

“虚拟化”在不同产品里覆盖范围不同。面试时别只报名字，先回答：**复用了什么资源，谁执行限制，邻居出问题会影响谁？**

- **硬件分区**：以 MIG 为例，在支持的设备上创建有明确资源边界的实例。规格与组合有限，不是任意比例，也不是独立物理主机。
- **软件共享或限制**：通过驱动调度、服务进程或软件组件复用设备。某些方案提供限额，某些只提供共享访问；必须按实现核对，不能一概说都有显存隔离。
- **虚拟机设备方案**：直通与 vGPU 关注虚拟机如何获得 GPU 能力，底层可能采用不同机制，还要核对驱动、平台和许可。

**时间片尤其容易误读。** 假设一张卡暴露 4 份共享访问名额，不代表每份都有独立的四分之一显存，也不承诺每个请求用时相同。见 [Time-slicing 与 MPS](/docs/gpu-virtualization/time-slicing-mps)。

## 两类“内存不足”，不要修错方向

### 容器 OOMKilled 与 CUDA OOM

`OOMKilled` 常提示主机内存或 cgroup 限制相关问题，应检查容器终止原因、事件和节点内存。退出码 137 本身表示相应的信号终止，不能单独证明是 GPU 显存不足，甚至不能单靠它认定发生了 OOM。

应用里的 `CUDA out of memory` 则首先指向设备内存分配问题。普通 Pod 的 `memory` 限制不是 GPU 显存配额，单纯把它调大通常不会解决设备显存不足。涉及卸载或统一内存时，还要分别检查主机和设备两侧的资源压力，不能把两者混成一个数字。

### nvidia-smi 显示占用很大，就是泄漏吗？

不一定。以 PyTorch 的缓存分配器为例：

- **allocated**：当前张量占用的内存。
- **reserved**：分配器管理的内存，包含正在使用的部分和保留供复用的空间。
- **设备工具看到的使用量**：还可能涉及上下文、其他库和进程等，不能简单等同于一个框架的 reserved。

张量释放后，框架可能保留空闲缓存供下次复用；缓存不等于泄漏。反过来，也不能看到“有缓存”就排除泄漏。持续增长、无法回落的活跃占用仍要查对象引用和任务生命周期。

### 发生显存 OOM，按什么顺序查？

先保留错误和负载条件，再检查实际可用容量、共享邻居和配额；然后核算权重、KV Cache、中间结果与临时缓冲；最后结合分配器信息检查缓存与碎片。**reserved 与 allocated 的差值大，不足以单独证明碎片是根因。**

释放未使用缓存不能释放仍被张量引用的内存，也不是通用扩容办法。不要未经诊断就把某个分配器配置写进所有生产任务。推理缓存的具体估算见 [KV Cache 容量计算](/docs/agent-general/llm-basics/model-adaptation-inference/model-inference)。

## GPU 利用率 100%，等于性能已经跑满了吗？

不等于。按 NVIDIA 对相应 GPU 利用率指标的定义，它主要反映采样窗口内有 kernel 执行的时间比例，不是直接测“发挥了多少峰值算力”。具体字段可用性与语义还要按设备及工具版本确认。

一张卡可以一直有工作，却主要在等数据或执行效率不高。判断服务是否健康，还要看请求完成量、排队、首字延迟、输出速度、显存与带宽等证据；平均利用率也不能代替最慢那部分请求的延迟。

共享方案是否有效，应对照独占基线测试，见 [性能与隔离验证](/docs/gpu-virtualization/benchmark-isolation)。

## 面试自测

**模型能装下，为什么并发一高就失败？** 每条请求还可能增加缓存、中间结果和其他开销，容量不能只算权重。

**装了 GPU Operator，就有每个租户独立显存了吗？** 没有这个保证。还要检查具体共享机制、资源申请和实际限制行为。

**为什么不把所有任务都共享在一张卡上？** 要考虑显存总量、延迟干扰、故障影响范围和兼容性；利用率提高不是唯一目标。
