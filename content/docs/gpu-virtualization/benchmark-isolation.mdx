## 面试题：怎样公平验证 GPU 共享方案的收益与隔离？

### 30 秒回答

比较 GPU 共享方案，先在同一环境测独占基线，再加邻居任务，看总吞吐、每个任务的延迟、显存和失败情况。卡越忙不一定服务越好：可能完成了更多总工作，却让关键用户等得更久。

### 用一个例子理解

餐厅出餐总量上升，不代表每桌客人都更快吃上饭。推理服务也要同时看 TTFT（等到首个 token 的时间）、TPOT（生成阶段平均每个输出 token 的耗时）和尾延迟（最慢那部分请求的等待情况），不能只展示 GPU 利用率。

### 关键机制与取舍

- 先弄清指标语义：设备利用率、显存占用、计算活跃度和带宽不是同一个百分比；硬件指标还要与请求排队、吞吐和延迟对应。不要照抄别的版本的监控字段编号，见 [GPU 扫盲中的指标解释](/docs/gpu-virtualization/gpu-basics)。
- 先做单任务基线，再逐步增加相同与不同类型邻居，覆盖短请求、长序列和突发流量。
- 区分 TTFT、TPOT、端到端耗时与排队，报告冷启动和热态、重复次数及波动。
- 在隔离测试环境验证显存超额、进程退出和设备异常影响，生产环境不做未授权破坏测试。

### 场景与失败处理

共享后总吞吐提高，但关键租户 P99 延迟超过目标。应调整租户分池、并发或实例规格，不能只展示吞吐提升而隐去服务质量下降。

### 常见追问

**如何测故障隔离？** 先明确预期故障域，再受控注入已授权故障并检查邻居状态、数据与恢复时间。

**结果怎样可复现？** 记录版本、配置、命令、负载种子和原始结果；未运行的步骤标明为计划。
