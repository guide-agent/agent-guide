## 面试题：如何设计单 Agent，并判断它是否已经不够用？

### 回答框架

单 Agent 可以有多次模型调用、多个工具和独立验证器，只是主要决策上下文由一个控制主体维护。先把目标、状态、工具契约和预算做好，建立可测基线；只有证据表明上下文、权限或可并行性成为瓶颈，才考虑拆成多 Agent。

### 关键机制与取舍

- 分离模型适配、上下文组装、工具执行、状态存储与结果验证，避免一个长函数承担全部责任。
- 对工具选择、参数错误和停止判断分别留测试，区分模型能力不足与工程实现缺陷。
- 同一 Agent 可先规划再执行；增加角色名不自动改善效果。

### 场景与失败处理

客服 Agent 频繁选错同名工具，先合并或改清工具职责并减少暴露范围；直接增加三个角色可能只把错误转化成更多通信。

### 常见追问

**何时拆分？** 出现稳定可独立验收的子任务，且专用上下文或权限隔离的收益超过通信开销时。

**验证器算第二个 Agent 吗？** 看是否具有独立决策闭环；规则验证器不必归为 Agent。
